# Обновление на Bothost и откат

Сборка подготовлена локально. Панель, тариф, фактическая база и права токенов пользователя не были доступны; развёртывание и реальные запросы WB не выполнялись.

## Перед заменой файлов

1. В панели Bothost остановите действующего бота. Не запускайте одновременно старую и новую версии с одним Telegram-токеном.
2. Скачайте резервную копию **всей папки data** и текущего кода. Сохраните настройки окружения, включая Telegram-токен и белый список. Не пересылайте токены в аналитические чаты.
3. Проверьте фактическое имя и путь действующей SQLite-базы. Этот архив не содержит вашей `.env` или рабочей БД.
4. Bothost рекомендует постоянные файлы в `/app/data`. Для этого проекта настройка — `DB_PATH=/app/data/bot.db`. Если существующая база имеет другое имя, сохраните его и укажите правильный путь; не создавайте случайно новую пустую базу вместо прежней.

Официальная инструкция по постоянному хранению: https://bothost.ru/docs/database-storage

## Установка

1. Замените файлы проекта содержимым архива. В корне должны оказаться `bot.py`, `requirements.txt` и остальные модули. Папку data и действующее окружение сохраните.
2. Точка запуска — `bot.py`, Python 3.11+ (Dockerfile использует 3.12). Установите зависимости из requirements.txt обычным механизмом Bothost. Не меняйте токены, пороги или время без необходимости.
3. Сохранены имена `TELEGRAM_BOT_TOKEN`, `ALLOWED_TELEGRAM_IDS`, `WB_TOKEN_SPB_TT`, `WB_TOKEN_SPB_TT_GROUP`. Также поддержан системный `BOT_TOKEN`, если отдельный TELEGRAM_BOT_TOKEN не заполнен.
4. Для Аналитики используйте существующие `WB_ANALYTICS_TOKEN_*`. Для раздельных категорий добавлены `WB_CONTENT_TOKEN_*`, `WB_PRICES_TOKEN_*`, `WB_ADS_TOKEN_*`. Пустое значение использует основной токен. Доступ проверяется запросом, а не наличием строки в настройках.
5. `WB_ENABLE_SEARCH=false` по умолчанию. Включайте только при уже имеющихся правах; подписка не покупается. `WB_ENABLE_STOCK_HISTORY=true` включает исторический CSV.
6. Запустите бота. При первом запуске схема дополняется автоматически, перед изменением существующей БД создаётся SQLite-копия в `data/backups`, проверяется integrity_check. Таблица user_settings и значения настроек не переписываются.

Новые таблицы имеют префикс `v3_`; схема фиксируется в schema_migrations. SQL для ревью — migrations/003_history.sql. Запускайте миграцию через приложение/maintenance, чтобы не обойти резервное копирование.

## После запуска

- Первая загрузка истории может идти несколькими проходами. Обзор не ждёт бесконечно необязательный источник. На страницах/таймаутах отображаются PARTIAL/ERROR и фактическое покрытие.
- Фоновая синхронизация запускается при старте и затем раз в 20 минут, с лимитами каждого источника. Один экземпляр защищён файловой блокировкой и блокировками загрузок в БД.
- Ежедневный обзор по прежним настройкам — 10:00 Europe/Moscow по умолчанию. При заметном уточнении (неполный итог стал полным или изменение известных единиц ≥3 и ≥5% через MAX этих порогов) отправляется новая ревизия.
- При неоднозначной ошибке доставки автоматический повтор блокируется, чтобы не дублировать сообщения. Вручную можно запросить `/overview` и `/excel`. Резервирование отправки не является гарантией exactly-once у внешнего Telegram API.
- Ежедневно в 00:30 создаётся согласованная SQLite-копия. Для полного восстановления дополнительно сохраняйте всю data, включая report_snapshots. Внешняя резервная копия вне хостинга обязательна для защиты от потери самого диска; бот её автоматически никуда не отправляет.
- Исторические ревизии сжаты в `data/report_snapshots`; старые отчёты не перезаписываются. Исходные buyer-ответы не сохраняются, диагностические метаданные без связей с фактами удаляются через 14 дней; важная связь с историей сохраняется.

## Проверка на реальных данных

Сверьте 10–20 карточек обоих кабинетов: лидеры, редкие, новые, размеры, нулевые заказы, неизвестные метрики. Для каждой проверки запишите nmID, период, время среза, источник и определение. Статистика заказов, продажи и рекламная атрибуция не обязаны совпадать.

Откройте новый пакет и проверьте «Качество данных», SourceStatus и MetricRegistry. Для исторических остатков количество лежит в колонке даты CSV, а warehouse_id в этом формате не предоставлен: сохраняется OfficeName, без выдуманного ID.

Объём полного ассортимента и лимит памяти тарифа не известны. Проверьте первую полную загрузку и расход диска/памяти. При крупном наборе бот переключается на ZIP (`REPORT_MAX_CELLS`, по умолчанию 450000 ячеек, `REPORT_MAX_BYTES` 45 МБ), сохраняя полные CSV. Если даже ZIP больше лимита, отправка прекращается с явным объяснением; данные остаются в БД, требуется выгрузка на сервере/увеличение разрешённого размера. Молчаливой обрезки нет.

## Административные команды в терминале Bothost

```text
python maintenance.py health
python maintenance.py backup
python maintenance.py templates
python maintenance.py import ProductMapping data/imports/ProductMapping.csv
python maintenance.py import Economics data/imports/Economics.csv
python maintenance.py action ACTION_ID DONE --owner "Ответственный" --due 2026-10-30
python maintenance.py export --date 2026-10-19 --out data/reports
python -m unittest -v
```

Импорт — локальное добавление подтверждённых аналитических данных, без изменений в WB. CSV: UTF-8 BOM, `;`, десятичный знак `.`, поля строго по шаблону. Перед изменением важных соответствий сделайте backup.

## Откат

1. Остановите бота в панели.
2. Сохраните текущую data отдельно, чтобы не потерять накопленные после обновления факты.
3. Восстановите прежний код и резервную копию прежней БД. Для SQLite предусмотрено:

```text
python maintenance.py restore data/backups/ИМЯ_КОПИИ.sqlite --bot-stopped
```

Перед восстановлением проверяется целостность копии и сохраняется ещё одна копия текущей БД. Команда не работает, пока новый процесс держит файловую блокировку. После отката удалять новые данные вручную не требуется: сохраните отдельную копию для последующего переноса.

4. Верните прежние переменные, если меняли пути, и запустите один экземпляр. Проверьте пользователя, порог, время и кабинеты.

Схема добавочная, но работа прежнего кода на расширенной базе вместо отката не является проверенной процедурой. Надёжный откат — прежний код + предмиграционная копия.
